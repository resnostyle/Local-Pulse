# Event Scraping Pipeline – Lean Architecture Design

## Overview

This system collects event data from multiple external sources, normalizes and deduplicates it, and serves it to a frontend with minimal infrastructure cost and complexity.

The architecture is designed to:

* Eliminate traditional databases
* Avoid long-running services
* Minimize cost via static hosting + CDN
* Remain scalable across locations
* Be deterministic and easy to debug

---

## High-Level Architecture

**Pipeline model (batch-oriented):**

1. Scrapers (fan-out)
2. Raw storage (source of truth)
3. Reducer (fan-in)
4. Processed static datasets
5. CDN delivery to frontend

---

## Core Principles

* Treat the system like a **static data compiler**, not a dynamic API
* Never mutate existing processed data incrementally
* Always rebuild outputs from raw inputs
* Partition data by **location** from day one
* Optimize for **read-heavy, infrequently changing data**

---

## Data Flow

### 1. Scraping Phase (Fan-Out)

Each scraper:

* Targets a single source (e.g., Eventbrite, Facebook)
* Runs independently
* Outputs normalized JSON

Output location:

```
/raw/{state}/{city}/{source}/{run_id}.json
```

Example:

```
/raw/nc/raleigh/eventbrite/2026-03-24T10-00.json
```

### Normalized Schema (example)

```json
{
  "source": "eventbrite",
  "source_id": "abc123",
  "title": "Food Festival",
  "start": "2026-03-24T18:00:00",
  "location": "raleigh",
  "venue": "Downtown",
  "url": "https://...",
  "raw_hash": "xyz"
}
```

---

### 2. Storage Layer

Raw data is stored in object storage and treated as immutable.

Characteristics:

* Append-only
* Debuggable
* Re-runnable

Raw data = **source of truth**

---

### 3. Triggering the Reducer

Scraper uploads trigger a reducer indirectly.

**Do NOT merge immediately on upload.**

Instead use one of:

#### Option A: Debounced Trigger (recommended)

* Upload triggers event
* Reducer runs after short delay (e.g., 1–2 minutes)
* Prevents race conditions

#### Option B: Scheduled Reducer

* Reducer runs every N minutes
* Ignores timing of individual scrapers

---

### 4. Reduce Phase (Fan-In)

The reducer:

* Reads all relevant raw files for a location
* Merges datasets
* Deduplicates events
* Normalizes fields
* Outputs final JSON files

**Important:**

* Always rebuild from raw
* Never patch existing processed files

---

## Deduplication Strategy

### Recommended Approach: Content Hash

Generate a deterministic ID using:

```
(title + start_time + venue)
```

Fallback:

```
source + source_id
```

Future improvement:

* Fuzzy matching (title similarity, time proximity, venue matching)

---

## Processed Output Structure

All processed data is partitioned by location.

```
/processed/{state}/{city}/
  index.json
  by-date/YYYY-MM-DD.json
  by-id/{event_id}.json
```

Example:

```
/processed/nc/raleigh/by-date/2026-03-24.json
```

---

## Location Strategy

All data is namespaced by:

```
/state/city
```

Example:

```
/processed/nc/raleigh/...
/processed/nc/durham/...
```

Benefits:

* No refactor needed for expansion
* Clean caching boundaries
* Independent scaling per location

---

## Global Index

Provides discovery across locations:

```
/events/index.json
```

Example:

```json
{
  "locations": [
    { "state": "nc", "city": "raleigh" },
    { "state": "nc", "city": "durham" }
  ]
}
```

---

## Serving Layer

Processed files are served via CDN.

Frontend directly fetches:

```
/events/locations/nc/raleigh/by-date/2026-03-24.json
```

No backend API required.

---

## Lambda Usage Strategy

Use serverless functions selectively:

### Good Use Cases

* Scrapers (short-lived)
* Reducer (if dataset is small)
* Event triggers

### Avoid

* Long-running jobs
* Incremental merging logic
* Complex orchestration early

---

## Anti-Patterns to Avoid

### 1. Incremental Merging

Avoid:

```
read → append → write
```

Problems:

* Race conditions
* Data corruption
* Duplicate amplification

---

### 2. Single Large Dataset

Avoid:

```
/events/all.json
```

Problems:

* Large payloads
* Poor caching
* Slow clients

---

### 3. Mixing Locations

Avoid:

```
/events/by-date/2026-03-24.json
```

Containing multiple cities.

---

## Scaling Strategy

### Horizontal Scaling

* Add new locations as folders
* Add new scrapers independently

### Performance Scaling

* Split large datasets into pages if needed

Example:

```
/by-date/2026-03-24/page-1.json
```

---

## Failure Handling

* If a scraper fails → reducer still runs
* Missing data is tolerated
* Next run corrects it

System remains operational at all times.

---

## Deployment Options

### Phase 1 (Recommended)

* Single scheduled job runs:

  * All scrapers
  * Reducer

### Phase 2

* Scrapers run independently (Lambda)
* Reducer runs on schedule or debounce trigger

### Phase 3 (if needed)

* Add workflow orchestration

---

## Mental Model

* Raw data = source code
* Reducer = compiler
* Processed data = compiled output

Never edit compiled output directly.

---

## Summary

This architecture:

* Removes the need for a database
* Eliminates backend APIs
* Minimizes infrastructure cost
* Scales cleanly across locations
* Remains simple to reason about

The key decision is to treat data generation as a **batch compilation step**, not a real-time system.
